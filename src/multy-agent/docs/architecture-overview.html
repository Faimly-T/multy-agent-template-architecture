The Problem

Why Multi-Agent? Why a Framework?

When you interact with Claude or ChatGPT, a single conversation handles everything: asking, reasoning, answering. That works well for simple tasks. But for complex, multi-step knowledge work — designing products, producing research, generating architecture documents — a single AI session hits limits fast: context overflow, no memory of prior sessions, no specialisation, no quality gates.

🧠

Context Window Problem

AI models have a fixed context window. Long tasks exceed it. Multi-agent splits the work across phases, each with a focused context.

🔁

No Session Memory

Each ChatGPT/Claude conversation starts fresh. Agents in this framework persist state in MARK files and resume exactly where they left off.

🎯

One Model Does Everything

A single agent tries to capture, organise, distill, and express simultaneously. Specialists outperform generalists — even in AI.

✅

This framework's answer: Each agent follows the same 5-phase CODE relay — capturing raw ideas, organising them, distilling them into concrete results, and expressing them as deliverables. A pipeline of typed steps enforces quality gates at every transition. Memory persists as structured markdown files across sessions.

Architecture

Three-Layer Architecture

The framework is split into three projects following clean architecture principles — each layer depends only on the one above it.

🔌

AgentFramework.Infrastructure — Adapters

Connects abstractions to the real world. AnthropicChatClient talks to Claude's API. FileSkillResolver reads SKILL.md files from disk. ServiceCollectionExtensions wires everything into .NET DI. Swap Claude for any other model by replacing this layer only.

🤖

AgentFramework.Domain — Agents

Where domain-specific agents live. UxPersona is an example: it extends AgentAggregate, declares its steps via UxStepBuilder, and inherits all session management, question tracking, and prompt composition for free.

⚙️

AgentFramework.Core — Framework

The engine. Contains AgentAggregate, PromptContext, the CODE step types, the KickoffChain handlers, all interfaces (ports), session domain objects (Question, Decision, Deliverable, IslandBacklog), and the skill record types. No agent-specific logic here.

Methodology

The CODE 5-Phase Relay

Every agent runs the same five phases in strict order — adapted from Tiago Forte's Capture → Organize → Distill → Express methodology for AI agent workflows. Think of it as an assembly line where each station produces a typed artefact that the next station consumes.

Phase 1
KickoffStep
Re-Hydrate
Read MARK files from disk. Triage open questions. Synthesise a clear Session Objective. Gate: objective is well-formed.
→
Phase 2
CaptureStep
Capture
DIVERGENT — generate an unfiltered Island Backlog. No judging. Quantity over quality. All ideas become typed islands.
→
Phase 3
OrganizeStep
Organize
CONVERGENT — deduplicate, cluster, and sequence the backlog. Produce an Execution Roadmap. Record architectural decisions.
→
Phase 4
DistillStep
Distill
Process each island into a concrete Result or formal Concern. Expert synthesis — the AI produces the actual deliverable content.
→
Phase 5
ExpressStep
Express & Relay
Write artifacts to disk. Update MARK files (including token usage). Emit a System Relay for orchestrator or next agent.
💡

The DIVERGENT → CONVERGENT boundary matters. Phase 2 (Capture) generates freely with no filtering. Phase 3 (Organize) then applies rigour. This prevents the common failure mode where the AI self-censors good ideas too early.

Key Design Patterns

How the Framework Is Built

Three interlocking patterns make the framework work. Understanding them unlocks the ability to extend it safely.

🏛️

Pattern 1 — DDD Aggregate (AgentAggregate<TId>)

Domain-Driven Design

The AgentAggregate is the single source of truth for an agent's runtime state. It owns everything: Role, Session, Pipeline, and the lists of Questions, Decisions, and Deliverables. Nothing mutates these directly — all writes go through role interfaces (ISessionWriter, IQuestionWriter, etc.), enforcing an invariant boundary.

Domain agents (like UxPersona) extend AgentAggregate<string> and receive their steps as a dependency — they never contain framework mechanics themselves.

// AgentAggregate owns execution — call one step at a time:
var result = await agent.ExecuteNextStepAsync(chatClient, ct);

// Or run all steps to completion in one call:
var runResult = await agent.RunAsync(userIntent, chatClient, writer, pipelineFactory, ct);

// Questions, decisions, deliverables are automatically tracked:
IReadOnlyList<Question>   questions   = agent.Questions;
IReadOnlyList<Decision>   decisions   = agent.Decisions;
IReadOnlyList<Deliverable> deliverables = agent.Deliverables;
🔒

Pattern 2 — Type State (PromptContext)

Immutable records Interface segregation

PromptContext is a single sealed immutable record that implements three interfaces — one for each architectural layer. Each layer receives only the interface it's allowed to use. This prevents a lower layer from accidentally reading the role, or a higher layer from calling BuildMessages prematurely.

Interface
Who receives it
What they can do
IAgentPromptLayer

Key invariant: ICommandPromptLayer.BuildMessages is the only place in the entire codebase where ChatMessage[] are created. It is never stored — only consumed immediately by IChatClient.

// Context flows downward — each layer enriches immutably:

// Aggregate level (IAgentPromptLayer):
IStepPromptLayer ctx = PromptContext.Empty.WithRole(Role);  // cached lazily

// Step/command level (IStepPromptLayer):
var withSkills = ctx.WithSkills(resolvedSkills).ForCommand;

// Terminal — ephemeral inside ResolveAndBuildAsync (ICommandPromptLayer):
IReadOnlyList<ChatMessage> msgs = withSkills.BuildMessages(instruction, userContent);
⛓️

Pattern 3 — Context Chain (CommandHandlerBase)

Chain of Responsibility Skill composition

Inspired by Denis Rothman's Context Engineering for Multi-Agent Systems, the KickoffChain runs five handlers in sequence. Each handler receives the accumulated context from all prior handlers in the chain journal — progressive context enrichment without a monolithic prompt.

CommandHandlerBase is the abstract base for all AI-calling handlers. Subclasses override SynthesisInstruction and optionally SkillNames or AutoSelectSkills. The base class handles all the prompt assembly.

Pattern A — Explicit skill names

Override SkillNames with a fixed list. The resolver fetches full instructions for exactly those skills, in that order. Deterministic — same skills every run.

protected override IReadOnlyList<string> SkillNames
    => ["kickoff-context-usingOKR"];

Pattern B — LLM-driven selection

Set AutoSelectSkills = true. The catalog (name + description only) is sent to the model. The model picks the relevant skills. Full instructions loaded only for selected ones.

protected override bool AutoSelectSkills => true;

The KickoffChain — 5 handlers in sequence

HandlerTypeWhat it produces
CheckpointValidatorCommandLLM · Role onlyValidates prior checkpoint — staleness, narrative bridge, gate status
MarkFileLoaderHandlerDeterministicReads MARK files from disk — no LLM, no context. Pure data loading.
IterationEvaluatorHandlerDeterministicEvaluates iteration state from session data — no LLM call
QuestionTriageHandlerLLM · Role onlyClassifies each open question as resolved / obsolete / still-open with severity

The Skill System

Skills — Composable Instruction Modules

If you've used custom instructions in ChatGPT or system prompts in Claude, you already understand skills conceptually. A skill is a block of markdown instructions that tells the AI how to perform a specific task. The difference here is that skills are files on disk, resolved lazily, and composed dynamically per command.

📄

Skills are SKILL.md files

Each skill is a markdown file with YAML frontmatter (name, description) and a body of instructions. Strategy is encoded in the name: kickoff-context-usingOKR vs kickoff-context-usingSMART.

🪶

Lazy, lightweight loading

GetCatalogAsync reads only frontmatter — fast. ResolveAsync loads full instructions only for selected skills. The AI never sees instructions it doesn't need.

📐

Ordered composition

Skills are injected into the system prompt in the order they were requested. Order controls priority. The same skill appears differently depending on what precedes it.

How a skill flows into a prompt

When a handler calls ResolveAndBuildAsync, the final system message is assembled in this order:

System message structure
1
Role prompt — who the AI is, its mandate, facts & directives. Set once at the Aggregate level via WithRole(role).
2
Skill blocks (0-N) — each resolved skill's instructions prepended with ### Skill: {name}. Added at command level via WithSkills(skills).
3
Synthesis instruction — the command-specific directive (what this particular handler needs the AI to do). From SynthesisInstruction.
The user message carries the dynamic context: prior handler outputs, session data, MARK file content, open questions, and user intent.

Skill record types

SkillSummary — Catalog entry

Lightweight: Name + Description only. Sent to the LLM for skill selection (Pattern B). Never contains full instructions — keeps the selection call cheap.

record SkillSummary(string Name, string Description);

Skill — Full record

Complete: Name + Description + Instructions. Returned by ResolveAsync after selection. Instructions are injected verbatim into the system prompt.

record Skill(string Name, string Description, string Instructions);
Extension Guide

Building a New Agent

Adding a new domain agent requires touching only the Domain and Infrastructure layers. The Core framework is unchanged. Here's what you need to create:

1

Create your Aggregate class

Extend AgentAggregate<TId>. Declare your typed ID, accept a Role and AgentStep[] in the constructor, build the pipeline with StepPipelineBuilder. No framework mechanics inside.

2

Author a ROLE.md file

A markdown file with the agent's Identity (name, domain), Mandate (what it must achieve), and Facts & Directives (domain rules the AI must never violate). Loaded by RoleParser at startup.

3

Configure your Steps

For each CODE phase, instantiate the matching step type (KickoffStep, CaptureStep, OrganizeStep, DistillStep, ExpressStep) with a step number, domain-specific instructions, and a Gate. Build the pipeline via your step builder.

4

Write SKILL.md files (optional)

If your agent uses skill-augmented steps, author SKILL.md files in the skills directory. Name them to encode strategy: capture-ux-persona, distill-journey-map. Each file has YAML frontmatter + markdown instructions.

5

Wire up in DI

Register your agent, IPipelineFactory implementation, ISkillResolver (FileSkillResolver if using file-based skills), and IChatClient (AnthropicChatClient for Claude) in the DI container.

Minimal domain agent — complete example

public class ProductOwnerAgent : AgentAggregate<string>
{
    public ProductOwnerAgent(
        Role       role,
        AgentStep[] steps,
        string     projectId,
        SessionMarkFilePaths markFilePaths)
        : base("product-owner-agent", role, projectId, markFilePaths)
    {
        Pipeline = new StepPipelineBuilder().WithSteps(steps).Build();
    }
}

// Steps configured externally (IPipelineFactory implementation):
var steps = new AgentStep[]
{
    new KickoffStep(1, "Define the product vision objective",   Gate.Required, markReader, skillResolver),
    new CaptureStep(2, "Capture all backlog ideas and requirements", Gate.Required),
    new OrganizeStep(3, "Prioritise by business value and risk",    Gate.Required),
    new DistillStep(4,  "Produce user stories and acceptance criteria",Gate.Required),
    new ExpressStep(5,  "Write roadmap and update MARK files",       Gate.Required),
};
💡

Gate.Required vs Gate.Advisory: A Required gate halts pipeline progression if gateSatisfied = false. An Advisory gate records the warning but continues. Use Required for structural quality checks (e.g. "session objective must be well-formed") and Advisory for optional enrichment steps.

Session Memory

Persistence & Cross-Session Continuity

Unlike a ChatGPT conversation that vanishes when you close the tab, agents in this framework maintain structured memory across sessions through MARK files — versioned markdown files written at the end of every session and read at the start of the next.

📋

Progress Summary MARK

What was accomplished, what threads are open, the session momentum, and full token usage for every run. Read by KickoffStep at Phase 1.

{prefix}_Progress_Summary_MARK.md
❓

Questions Log MARK

All open, resolved, and obsolete questions the agent raised. Restored into the aggregate on session start. Triaged by QuestionTriageHandler automatically.

{prefix}_Questions_Log_MARK.md
📚

Distill History MARK

Append-only log of every distillation run across all sessions: islands processed, decisions made, artifacts produced. The AI can reference prior work without starting over.

{prefix}_Distill_History_MARK.md

Domain objects tracked inside the Aggregate

❓ Questions

Raised during any step. Status lifecycle: Open → Answered → Reviewed (or Obsolete). Can be answered between sessions via agent.SupplyAnswers(...).

📌 Decisions

Recorded during Organize phase. Each has an ID, description, and impact. Persisted to ADR-XXX-{title}.md files by the Express step.

📦 Deliverables

Produced during Distill phase. Each has a path and a status (Pending / Written / Failed). Tracked so the orchestrator knows what was actually produced.

Token budget tracking

Every session records its token consumption in the Progress Summary MARK. This enables budget awareness across long-running projects:

| Metric              | Value     |
|---------------------|-----------|
| Input tokens        | 12,450    |
| Output tokens       |  3,120    |
| Total tokens        | 15,570    |
| Est. % of 5h budget |   ~2.8%   |
Extensibility Summary

What You Can Extend vs What You Inherit

Concern You implement Framework provides
Domain agent Extend AgentAggregate<TId>, set pipeline All session management, prompt context, question/decision/deliverable tracking
Agent role Author ROLE.md with identity + mandate + directives RoleParser reads it, PromptContext.WithRole() injects it
Step instructions Pass domain-specific instruction strings to step constructors AgentStep base class, DefaultStepCommand, JSON schema enforcement
Skills Author SKILL.md files with YAML frontmatter + instructions FileSkillResolver, catalog + resolve, lazy loading, Pattern A & B selection
LLM provider Implement IChatClient All prompt assembly, JSON parsing, step result type mapping
Custom handler chain Extend CommandHandlerBase, override SynthesisInstruction ResolveAndBuildAsync, both skill selection patterns, BuildMessages
Deliverable writing Implement IDeliverableWriter Called automatically at end of RunAsync with full run results
🚀

Bottom line: To add a new agent specialised in, say, competitive analysis — you write a ROLE.md, optionally a few SKILL.md files, create a class that extends AgentAggregate, and configure five steps with your domain instructions. The framework handles session hydration, prompt composition, question tracking, gate enforcement, MARK file persistence, and token monitoring automatically.
