AgentFramework

Architecture Reference — Multi-Agent Template System

1. Architecture Overview

AgentFramework is a structured, pipeline-driven AI-agent platform built on .NET 8. Each agent executes a fixed sequence of steps (Kickoff → Capture → Organize → Distill → Express). Every step calls an LLM via a clean port interface, parses a typed result, and applies domain mutations through a single ISessionWriter gateway.

Core Principles

  • Steps are immutable definitions; state lives in the aggregate
  • LLM is infrastructure — Core never imports it
  • Gate = named boolean condition; pipeline only advances when gate is satisfied
  • All state mutations go through StepResult.ApplyTo(ISessionWriter)

Dependency Flow

  • Core → no external deps
  • Domain → Core only
  • CodePipeline → Core + Domain
  • Infrastructure → Core (implements ports)
  • Host/Tests → wires everything together

3. Domain Model

Island Lifecycle

An Island is the atomic unit of captured knowledge — a single idea, requirement, or observation extracted from the user intent.

stateDiagram-v2 [*] --> Captured : CaptureStep Captured --> Organized : OrganizeStep (groups assigned) Organized --> Distilled : DistillStep (promoted) Organized --> Discarded : DistillStep (rejected) Distilled --> [*] Discarded --> [*]

Question Lifecycle

Questions are raised during Distillation and resolved between agent sessions (by a human, orchestrator, or another agent).

stateDiagram-v2 [*] --> Open : RaiseQuestion (DistillStep) Open --> Answered : SupplyAnswers (between sessions) Answered --> Reviewed : ExpressStep (answer incorporated) Open --> Obsolete : ExpressStep (no longer relevant) Answered --> Obsolete : ExpressStep

Core Entities

Island

  • Id — unique identifier
  • Content — the captured text
  • Status — Captured | Organized | Distilled | Discarded
  • GroupId — assigned by OrganizeStep
  • Tags — semantic labels

Question

  • Id — e.g. UX-Q001
  • Text — question body
  • Source — which step raised it
  • Status — Open | Answered | Reviewed | Obsolete
  • Answer / AnswerSource — set externally

Decision

  • Id — unique identifier
  • Description — what was decided
  • Impact — scope/severity label
  • GroupId — optional group association

Deliverable

  • DeliverableId
  • Path — relative output path
  • Status — e.g. pending | complete
  • GroupId / Purpose — optional

AgentSession

The AgentSession is a value snapshot that travels with the aggregate. It holds: the current UserIntent, the IslandBacklog, a list of IslandGroups, token consumption counters, and iteration history.

4. Key Interfaces

IChatClient — the LLM Port

public interface IChatClient
{
    // Used by DefaultStepCommand (non-chain steps like Express)
    Task<string> SendAsync(
        IReadOnlyList<ChatMessage> messages,
        string? jsonSchema,
        CancellationToken ct);

    // Used by chain handlers — jsonSchema is IGNORED by AnthropicChatClient
    Task<string> SendHandlerAsync(
        IReadOnlyList<ChatMessage> messages,
        string? jsonSchema,
        CancellationToken ct);
}

ISessionWriter — the Mutation Gateway

{

Step Detail Cards

Step 1 KickoffStep

Single LLM call (no chain). Extracts a structured session objective from raw user intent. Uses DefaultStepCommand which auto-injects the JSON schema into the prompt.

Writes: Session.Objective

Step 2 CaptureStep

Chain: IslandFromObjectiveHandler → IslandFromQuestionsHandler. Extracts knowledge islands; second handler also captures islands from open questions.

Writes: Session.Backlog (Captured islands)

Step 3 OrganizeStep

Chain: IslandGroupingHandler → GroupReadinessHandler. Groups islands by theme; assesses group readiness for distillation.

Writes: Session.Groups, Decisions

Step 4 DistillStep

Chain: GroupDistillationHandler (runs per group). Promotes islands to deliverables, records decisions, raises blocking questions.

Writes: Deliverables, Decisions, Questions

Step 5 ExpressStep

Single LLM call (no chain). Reviews questions, updates token consumption, produces a human-readable summary of the session.

Writes: token stats, question statuses

6. Chain & Handler Pattern

Steps that need multiple LLM calls use an IStepChain. Each CommandHandlerBase owns one LLM call, builds its own prompt, and writes its typed output into a shared HandlerExchange journal.

sequenceDiagram participant Step participant Chain as IStepChain participant H1 as Handler 1 participant H2 as Handler 2 participant LLM as IChatClient Step->>Chain: RunAsync(context, promptLayer, chatClient) Chain->>H1: RunAsync(exchange) H1->>H1: BuildUserContent(exchange) H1->>LLM: SendHandlerAsync(messages, schema) LLM-->>H1: JSON string H1->>H1: ParseResponse(json) → typed record H1->>Chain: exchange.Record(result) Chain->>H2: RunAsync(exchange) H2->>H2: reads H1 result from exchange.Get<T>() H2->>LLM: SendHandlerAsync(messages, schema) LLM-->>H2: JSON string H2->>Chain: exchange.Record(result) Chain-->>Step: HandlerExchange (all results) Step->>Step: ParseResult(exchange) → StepResult

Implementing a Handler

internal class MyAnalysisHandler(IStepPromptLayer promptLayer)
    : CommandHandlerBase("my-analysis", promptLayer)
{
    // ⚠️ CRITICAL: embed schema verbatim — SendHandlerAsync ignores the jsonSchema param
    private const string AnalysisSchema = """
        {
          "findings": [
            { "id": "F-001", "category": "string", "summary": "string", "priority": "high|medium|low" }
          ],
          "confidence": 0.95
        }
        """;

    protected override string BuildUserContent(HandlerExchange exchange)
    {
        // read prior handler result if needed
        var upstream = exchange.Get<CaptureHandlerResult>();

        return $"""
            Analyze the following captured islands:
            {FormatIslands(upstream.Islands)}

            Respond using EXACTLY this JSON structure — use these field names verbatim:
            {AnalysisSchema}
            """;
    }

    protected override HandlerResult ParseResponse(string json)
    {
        using var doc = JsonDocument.Parse(json);
        // ... parse findings ...
        return new MyAnalysisResult(findings);
    }
}

HandlerExchange

HandlerExchange is a typed journal passed through the chain. Handlers write typed records using exchange.Record(result) and read upstream results using exchange.Get<T>(). The final step reads the complete exchange to build its StepResult.

Schema embedding is mandatory for chain handlers. Without the JSON schema embedded in the user message, the LLM will invent field names (e.g. groupId instead of id), and the parser will silently produce empty collections — causing gate failures with no error thrown.

8. Prompt Layers & Skill System

Prompt construction is layered. Each layer adds context without the step knowing about it. The IStepPromptLayer port abstracts this so any provider (file-based, in-memory, or composited) can be plugged in.

Layer 1 — System Role

Agent identity, persona, core capabilities. Set via RolePromptAgentContext passed to the aggregate constructor. Example: "You are a senior software architect specialising in DDD…"

Layer 2 — Step Instructions

Per-step instructions set at step creation time (instructions parameter). Describes the goal and constraints of that specific step.

Layer 3 — Dynamic Context

Generated by step.BuildContext(IAgentRunContext) at call time. Injects current state: islands, deliverables, questions, token stats.

Layer 4 — Schema

For non-chain steps: injected automatically by DefaultStepCommand from step.JsonResponseSchema. For chain handlers: must be embedded manually in the user message.

DefaultStepCommand — Non-Chain Prompt Structure

// What DefaultStepCommand appends to the user message automatically:
"""
### Required Response Format
Respond ONLY with a JSON object matching this schema:
```json
{schema}
```
Gate: {gate}
"""

9. Implementing New Agents

New agents follow an 8-step recipe. The framework is designed so you only need to create the steps that differ from the standard pipeline — inherit the rest.

Step-by-Step Checklist

① Define the Agent Class

Extend AgentAggregate<TId>. Set up the pipeline in the constructor.

public class SecurityAuditAgent : AgentAggregate<Guid>
{
    public SecurityAuditAgent(Guid id, string projectId, IStepPromptLayer rolePrompt)
        : base(id, projectId, rolePrompt)
    {
        Id = id;
        Pipeline = SecurityAuditPipelineFactory.Build(rolePrompt);
    }
}

② Create a Pipeline Factory

Assemble the StepPipeline with the steps in order.

public static class SecurityAuditPipelineFactory
{
    public static StepPipeline Build(IStepPromptLayer rolePrompt)
    {
        var gate = new Gate("security-audit-complete");

        return new StepPipeline([
            new KickoffStep(rolePrompt, 1, "Clarify the security audit scope.", gate),
            new CaptureStep(rolePrompt, 2, "Extract security concerns.", gate),
            new ThreatModelStep(rolePrompt, 3, "Model threats per STRIDE.", gate),
            new RemediationStep(rolePrompt, 4, "Propose remediations.", gate),
            new ExpressStep(rolePrompt, 5, "Summarise findings and open questions.", gate),
        ]);
    }
}

③ Define Custom Step Results

Create typed records that extend StepResult and implement ApplyTo.

public record ThreatModelResult(
    string Output,
    bool GateSatisfied,
    IReadOnlyList<ThreatRecord> Threats) : StepResult(Output, GateSatisfied)
{
    public override void ApplyTo(ISessionWriter writer)
    {
        foreach (var threat in Threats)
        {
            // Raise a question for each high-severity threat
            if (threat.Severity == "high")
                writer.RaiseQuestion(threat.Id, threat.Description, "threat-model");
        }
    }
}

public record ThreatRecord(string Id, string Description, string Severity, string Stride);

④ Implement the Custom Step

Extend AgentStep. Provide the JSON schema and parse logic.

public class ThreatModelStep : AgentStep
{
    public ThreatModelStep(IStepPromptLayer ctx, int num, string instructions, Gate gate,
        IStepChain? chain = null)
        : base(ctx, num, "threat-model", instructions, gate, chain) { }

    public override string JsonResponseSchema => """
        {
          "threats": [
            {
              "id": "T-001",
              "description": "string",
              "severity": "high|medium|low",
              "stride": "S|T|R|I|D|E",
              "affectedComponent": "string"
            }
          ],
          "gateSatisfied": true
        }
        """;

    public override string BuildContext(IAgentRunContext? context)
    {
        if (context is null) return "No context.";
        var islands = context.Session?.Backlog?.GetAll()
            .Select(i => $"- {i.Content}") ?? [];
        return $"Captured concerns:\n{string.Join("\n", islands)}";
    }

    public override StepResult ParseResult(JsonElement root, string rawOutput, bool gateSatisfied)
    {
        var threats = new List<ThreatRecord>();
        if (root.TryGetProperty("threats", out var arr))
            foreach (var el in arr.EnumerateArray())
                threats.Add(new ThreatRecord(
                    el.GetProperty("id").GetString() ?? "",
                    el.GetProperty("description").GetString() ?? "",
                    el.GetProperty("severity").GetString() ?? "low",
                    el.GetProperty("stride").GetString() ?? ""));

        return new ThreatModelResult(rawOutput, gateSatisfied, threats);
    }
}

⑤ Add Chain Handlers (if needed)

For multi-call steps, implement handlers and wire them into a chain.

// If ThreatModelStep needs two LLM calls:
var chain = new SequentialStepChain([
    new ThreatIdentificationHandler(rolePrompt),
    new ThreatScoringHandler(rolePrompt),
]);
new ThreatModelStep(rolePrompt, 3, instructions, gate, chain);
Remember: every handler must embed its JSON schema in the user message content. Do not rely on the jsonSchema parameter being forwarded to the API.

⑥ Extend the Aggregate (optional)

If your agent needs domain-specific collections or query methods, extend the aggregate.

public class SecurityAuditAgent : AgentAggregate<Guid>
{
    // Add domain-specific outputs
    private readonly List<ThreatRecord> _threats = [];
    public IReadOnlyList<ThreatRecord> Threats => _threats.AsReadOnly();

    // Expose a mutation method that downstream results can call
    public void AddThreat(ThreatRecord threat) => _threats.Add(threat);
}

Then in ThreatModelResult.ApplyTo, cast the writer to your concrete type: 

public override void ApplyTo(ISessionWriter writer)
{
    if (writer is SecurityAuditAgent agent)
        foreach (var t in Threats)
            agent.AddThreat(t);
}

⑦ Register the Deliverable Writer

Implement IDeliverableWriter to materialise outputs (files, API calls, database records). Called by RunAsync after all steps, regardless of gate satisfaction. 

public class SecurityReportWriter : IDeliverableWriter
{
    public async Task WriteAsync(
        IAgentRunContext context,
        IReadOnlyList<StepResult> results,
        CancellationToken ct)
    {
        var threats = results
            .OfType<ThreatModelResult>()
            .SelectMany(r => r.Threats)
            .ToList();

        var report = SecurityReportBuilder.Build(threats, context.Decisions);
        await File.WriteAllTextAsync("security-report.md", report, ct);
    }
}

⑧ Write & Wire Tests

Test each layer in isolation:

  • Unit tests — mock IChatClient, test ApplyTo in isolation
  • Step tests — feed canned JSON through step.ParseResult()
  • Integration tests — use a real AnthropicChatClient against the live API (tag [LiveApi])
[Fact]
public void ThreatModel_ParseResult_ExtractsThreats()
{
    var step = new ThreatModelStep(PromptContext.Empty, 3, "", new Gate("g"));
    using var doc = JsonDocument.Parse("""
        {"threats":[{"id":"T-001","description":"SQL injection","severity":"high","stride":"T","affectedComponent":"API"}],
         "gateSatisfied":true}
        """);

    var result = (ThreatModelResult) step.ParseResult(doc.RootElement, "", true);

    Assert.Single(result.Threats);
    Assert.Equal("T-001", result.Threats[0].Id);
    Assert.Equal("high", result.Threats[0].Severity);
}

10. Express Step Design Options

The Express step is the only step in AgentFramework.CodePipeline (the others live in AgentFramework.Domain). It is intentionally thin by default — a single relay call. Here are the four architectural patterns you can choose from.

1

Default LLM Relay

Current implementation Simplest

A single DefaultStepCommand call. The LLM receives deliverables, island stats, decisions, and the full question list. It returns token counts, updated question statuses, and a natural-language summary. 

// JsonResponseSchema already has questions[], inputTokens, outputTokens, gateSatisfied
// ExpressResult.ApplyTo calls writer.ReviewQuestion for every question returned
// New open questions the LLM discovers are auto-created via ReviewQuestion(id, Open, text)
Pros
  • Zero extra code
  • LLM synthesises across all steps
  • Handles question discovery organically
Cons
  • LLM may hallucinate question statuses
  • Non-deterministic token reporting
  • Hard to unit-test without mocking LLM
2

Chain-Based with Parallel Writers

Structured Recommended for production

Split the Express step into two chain handlers: NarrativeSummaryHandler (writes the human-readable summary) and QuestionReviewHandler (deterministically updates question statuses). The second handler runs in parallel or sequentially. 

var expressChain = new SequentialStepChain([
    new NarrativeSummaryHandler(rolePrompt),  // free-form summary, no JSON needed
    new QuestionReviewHandler(rolePrompt),    // structured JSON: question status updates
]);

new ExpressStep(rolePrompt, 5, instructions, gate, chain: expressChain);

In QuestionReviewHandler.BuildUserContent:

return $"""
    For each question below, decide the new status.
    {BuildQuestionsBlock(exchange.Context.Questions)}

    Respond using EXACTLY this JSON structure:
    {ReviewSchema}
    """;
Pros
  • Deterministic question management
  • Summary is free-form (better quality)
  • Each handler is independently testable
Cons
  • Two LLM calls (extra latency/cost)
  • More boilerplate
3

IDeliverableWriter Post-Processing

Offline Event-driven style

Keep ExpressStep minimal. Move the "what to do with results" logic entirely into the IDeliverableWriter. The writer receives all StepResult objects and the full IAgentRunContext — it can call external services, write files, publish events, or forward questions to a message bus. 

public class SlackNotifyingWriter : IDeliverableWriter
{
    public async Task WriteAsync(IAgentRunContext ctx, IReadOnlyList<StepResult> results,
        CancellationToken ct)
    {
        // Post deliverables to Jira
        foreach (var d in ctx.Deliverables)
            await _jira.CreateIssueAsync(d, ct);

        // Route open questions to another agent
        var openQs = ctx.Questions.Where(q => q.Status == QuestionStatus.Open).ToList();
        if (openQs.Any())
            await _questionRouter.RouteAsync(openQs, ct);
    }
}
Pros
  • Clean separation: LLM vs side-effects
  • No extra LLM calls for plumbing
  • Fully testable without LLM
Cons
  • No LLM synthesis in the writer
  • Question routing logic outside the domain
4

Hybrid: LLM Narrative + Chain Writers

Flexible Best quality

Three-handler chain: NarrativeHandler (LLM free-form summary), QuestionReviewHandler (LLM structured JSON for question statuses), DeterministicFinalizeHandler (no LLM — reads exchange results, calculates actual token totals from step conversations, emits the final structured payload). 

var chain = new SequentialStepChain([
    new NarrativeHandler(rolePrompt),           // LLM: free-form summary
    new QuestionReviewHandler(rolePrompt),       // LLM: structured question review
    new TokenTallyHandler(TokenSource.FromContext), // Pure: sums actual token usage
]);

TokenTallyHandler reads exchange.Context.StepConversations to compute real input/output token totals from the conversation log rather than asking the LLM to self-report.

Pros
  • Accurate token accounting
  • High-quality summary
  • Deterministic finalisation
Cons
  • Most complex implementation
  • Three handlers = more moving parts

Pattern 1 — Sequential Sessions (same agent)

The simplest pattern: run the same agent twice. Between sessions, supply answers externally.

// Session 1
var result1 = await agentA.RunAsync("Design the auth module", chatClient, writer);

// Inspect open questions
var openQs = agentA.GetOpenQuestions();
// → [UX-Q001: "What token expiry should we use?", ARCH-Q002: "Redis or in-process cache?"]

// Human or another agent resolves them
agentA.SupplyAnswers([
    ("UX-Q001", "15 minutes for access, 7 days for refresh", "product-owner"),
    ("ARCH-Q002", "Redis — we need distributed session support", "architect"),
]);

// Session 2 — CaptureStep will see both questions as Answered in BuildContext
var result2 = await agentA.RunAsync("Implement auth module (answers available)", chatClient, writer);

Pattern 2 — Direct Agent-to-Agent

Agent A's IDeliverableWriter spawns Agent B as a sub-task.

public class OrchestratingWriter(IChatClient chatClient) : IDeliverableWriter
{
    public async Task WriteAsync(IAgentRunContext ctx, IReadOnlyList<StepResult> results,
        CancellationToken ct)
    {
        var securityQs = ctx.Questions
            .Where(q => q.Id.StartsWith("SEC-") && q.Status == QuestionStatus.Open)
            .ToList();

        if (!securityQs.Any()) return;

        // Spawn a specialised security agent to answer security questions
        var secAgent = new SecurityAuditAgent(Guid.NewGuid(), ctx.Session!.ProjectId, secPrompt);
        var secResult = await secAgent.RunAsync(
            $"Answer these security questions: {FormatQuestions(securityQs)}",
            chatClient, NoOpWriter.Instance, ct);

        // Extract answers from security agent's deliverables/decisions
        var answers = ExtractAnswers(secResult, securityQs);

        // Feed answers back to the originating agent for session 2
        _agentA.SupplyAnswers(answers);
    }
}

Pattern 3 — Question Broker Service

A centralised IQuestionBroker service routes questions by ID prefix to the appropriate specialist agent. Questions are enqueued after each session and processed asynchronously. 

public interface IQuestionBroker
{
    Task EnqueueAsync(string originAgentId, IReadOnlyList<Question> questions, CancellationToken ct);
    Task<IReadOnlyList<AnswerRecord>> WaitForAnswersAsync(string originAgentId, CancellationToken ct);
}

// Routing rules (configure in DI / appsettings)
broker.RegisterRoute("UX-",   uxAgent);
broker.RegisterRoute("SEC-",  secAgent);
broker.RegisterRoute("ARCH-", archAgent);
broker.RegisterRoute("*",    humanReviewQueue);

Pattern 4 — Hub Orchestrator

A dedicated OrchestratorAgent (itself an AgentAggregate) runs first, decomposes the work into sub-problems, spawns specialised agents in parallel, collects their deliverables, and aggregates results. Each specialist agent raises its own questions; the orchestrator collects and routes them.
